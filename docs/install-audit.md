# Install audit

The current entry point is [guided setup](quickstart.md): install the skills, run `/agent-factory`, and one local
bootstrap command does GitHub workspace creation, backend sign-in, profile, locally stored secrets, your own GitHub App,
deployment and factory MCP details; then the connectors and the first launch.
This page records its remaining gaps. Source inspection and offline checks do not prove a fresh installation.

## Current boundaries

| Area | Supported procedure | Remaining gap |
|---|---|---|
| Bootstrap | Public [engine](https://github.com/unionai-oss/flyte-agent-factory) with `ops/bootstrap.py` run locally from one copy-paste command; the workspace template is bundled in the engine | Planned, not built: a hosted setup app and full install parity through the factory MCP. `unionai-oss/flyte-agent-workspace` does not exist yet; publishing it is optional. The bootstrap command and the `skills/dist/*.zip` links resolve only once this change is on `unionai-oss/flyte-agent-factory` `main`; until then they return 404 |
| Chat repository creation | Use the connector's `create_repository` on request, otherwise the bootstrap's `gh repo create --private` | Repository-scoped chat access does not imply repository creation or Projects access |
| Local preparation | `uv sync --python 3.12`, existing config/profile checks and profile validation | Chat without a local shell hands commands to the person; a remote shell is not their laptop |
| Credentials | Existing local helper for Claude token; temporary deploy-key file uploaded to Flyte | Helper replaces a token, so resume skips it unless rotation is needed; if secret storage fails after the public deploy key is uploaded, the bootstrap deletes the public key itself and removes the key directory, so a rerun starts clean |
| Shared state | Add `[state] uri` to either copied personal profile; administrator provisions native object storage and permissions; run the selected-provider probe locally | Examples omit state; every launch needs it. Runtime and local cloud identities need independent grants; no automatic storage provisioning |
| Deployment bootstrap | The bootstrap's `deploy` step mints a deployment API key for the run (`agent-factory-deploy`, default policies), records its client id in the workspace clone's git config before using it, hands it to both deploy scripts as `_UNION_EAGER_API_KEY` and deletes it when the run ends; a key you export as `_UNION_EAGER_API_KEY` is used instead and never deleted. By hand (fallback, [quickstart](quickstart.md) manual reference): create/reuse an encoded Union deployment key, grant deployment permissions, load `_UNION_EAGER_API_KEY` with a non-echo prompt, unset after the second factory deploy | Whether a key with the default policies may deploy is unverified on a real tenant. Selected Flyte config alone does not populate the child process environment; a chat MCP key need not have deploy permissions |
| Setup skill | One public package, `skills/dist/agent-factory.zip` (with `skills/dist/since.zip` beside it for `/since`), downloaded from GitHub and saved in claude.ai or `~/.claude/skills`; `/agent-factory` runs guided setup, then takes over | Claude app installation remains a UI step; a stale install is detected with `ops/package_skill.py --check` or the skill's own version check |
| First deployment | Existing scripts deploy fetched `origin/main`; retain successful steps | Images/builds require backend access and compute; this is not an offline connection test |
| MCP URL | First deploy returns app URL, update `[mcp] public_url`, deploy factory again | Two passes; app deployment does not prove client authentication |
| Claude Code | HTTP MCP with Union bearer header | User must configure a scoped Union key locally |
| claude.ai | Request-header custom connector where that beta is available | Stock app lacks OAuth discovery metadata; ordinary OAuth-only setup cannot connect. Use Claude Code if headers are unavailable |
| OSS Flyte | Core runtime primitives described in [compatibility audit](oss-flyte-compat.md) | Current installer is Union-specific; builds, initialization, child attachment and MCP auth require adaptation. Union keys and hosted app auth are not OSS capabilities |
| Output delivery | Workspace push by deploy key, optional `[github]` App for draft PRs/statuses | Without the App, output goes to the default branch and no PR opens; operator GitHub connector is a separate credential |
| Codex | Optional personal example and [credential procedure](engines.md#codex-credentials) | Claude token still required; placeholder/deploy/device-sign-in sequence has no end-to-end evidence here |

## Setup walkthrough verification

Each row classifies the handoff separately from evidence. **Chat-done** means chat can perform the action
with an available tool and must read back its result; it is not a claim that a user's setup was completed here.
**One copy-paste command** means chat prepares the existing command with confirmed non-secret values at the
moment needed, and the person runs it locally. **UI/admin** means a person must use settings or obtain access;
chat states the prerequisite and the next check. claude.ai has no local shell. No credential belongs in chat.

**RUN source** means code was read; **RUN offline** means an operation ran in isolation. The runnable doc
checks are `bash factory-improvement/checks.sh -n 16` (the default `not slow` lane plus lint/format).
`test_setup_operator_prepares_filled_in_handoffs_at_the_step_that_needs_them` checks the CODEOWNERS,
filled-in profile/state, URL and both policy/client-ID handoffs; it does not execute chat-generated edits.
`test_install_audit_classifies_every_step_and_keeps_external_work_not_run` checks this matrix's coverage.
Fresh-tenant, credential acceptance and client UI work remain **NOT RUN**; each row gives the local/source
substitute and the next external check.
