### Things this environment has already cost time on

- **A restart loses your Python environment, and your running children do not stop.** This pod can be replaced at any time -- a killed container leaves no log at all, so the first you know of it is finding yourself resumed. The checkpoint restores the workspace and the conversation; it does not restore a virtualenv you built outside it, and the subprocesses that launched your child actions are gone.
  - **Before relaunching anything after a restart, look at what is still running.** Child actions keep going on the cluster even though the process that launched them died, so relaunching duplicates work you are already paying for -- and on a GPU that is expensive:

    ```python
    import flyte, flyte.remote as remote
    from flyte_agent_factory.child import attach

    attach()
    run = flyte.ctx().action.run_name
    for a in remote.Action.listall(for_run_name=run):
        print(a.name, a.phase)   # wait on the RUNNING ones, do not resubmit them
    ```

    That listing is **read-only**, and it is the whole run: `a0` (the project itself), your own children, other sessions' children and every sub-agent. Most of it is not yours. Never abort anything from it, and never choose what to abort by matching names, phases or task names.

  - **Write down how to rebuild your environment** -- a `requirements.txt` you can reinstall from in one command, committed. A venv *inside* the workspace does survive, because the workspace is checkpointed at a stable path, but it is also then copied to object storage every few minutes: fine for a handful of small packages, wrong for a multi-gigabyte ML stack. Put heavy dependencies in a child action's image instead.
- **You run as an unprivileged user.** Nothing may assume it can write outside `$HOME` or `/tmp`. This broke three separate things before it was understood, so derive writable paths from `$HOME` and never hardcode `/var/lib`, `/state` or `/usr/local/bin`.
- **A Flyte code bundle carries Python modules, not package data.** Anything that is not a `.py` has to go into the image, or it is present locally and silently absent in the container.
- **Building an image is not running it.** An image that builds can still exit on its first line. Prove a component starts.
- **Rootless podman is installed** (vfs storage, chroot isolation), so `podman pull` and a `podman build` without `RUN` steps work in place. A `RUN` step or `podman run` also needs the cluster to allow nested user namespaces and /proc mounts, which many do not: try a one-line build first, and on `Operation not permitted` build through `flyte.sandbox.create` instead.

### Running work on the cluster

**Your own subagents first.** The roles in `.claude/agents/` are threads of this process, sharing this container and workspace. Right for reading, reviewing and parallel edits, and free. The roles, each with when to use it and the file it writes: `scope` (start of a project, or the brief is ambiguous or drifting) writes the ACCEPTANCE.md criteria draft; `discover` (a problem-brief issue, or a design question the code cannot answer) writes DISCOVERY.md; `prototype` (a choice between shapes a person will see or use) writes prototypes/ with at least two runnable options and an evaluation; `shape` (before building, or when a design fights the problem) writes DESIGN-RATIONALE.md; `build` (the shape is settled) writes code and tests; `verify` (after any build) gives evidence-cited verdicts. Each reads what the stage before it wrote, except `verify`, which reads only the criteria and the artifact. For a problem-brief issue -- the brief says the design is to be produced -- the order is `scope`, `discover`, `prototype` (when a person will see or use the result), `shape`, `build`, `verify`. The old names `product`, `designer`, `dev` and `qa` still work as aliases this release. Run **several `verify` at once** on different aspects. `DESIGN.md` holds the house rules they all follow; read it before you write anything.

**For anything needing its own hardware, submit a child action of this run.** Attach to the run once, then write ordinary Flyte:

```python
import asyncio, flyte
from flyte_agent_factory.child import attach

attach()

env = flyte.TaskEnvironment(
    name='train',
    image=os.environ['FLYTE_INTERNAL_IMAGE'],   # an image that already exists
    resources=flyte.Resources(cpu=2, memory='8Gi'),
)

@env.task
async def train(lr: float) -> float:
    ...

print(asyncio.run(train(0.01)))
```

Each gets its own container, hardware, logs and row in the run. Read `flyte_agent_factory/child.py` before your first one.

**Stopping a child you started** (an orphan, a runaway) is done with exact names, from the record `attach()` keeps of what you submitted:

```bash
python -m flyte_agent_factory.child abort <action-name> [<action-name> ...]
```

It refuses, and aborts nothing, for `a0`, your own action, a name you did not start, or anything that is not a plain name. **Aborting `a0` ends the whole project and discards everything since the last checkpoint** -- never abort it, never use `flyte abort` or `Action.abort` yourself, and never touch an action that another agent or a sub-agent started. If you think one of those is stuck, say so in your final message or ask the human.

**Two rules that will bite you otherwise:**

1. **The image must already exist.** Submission succeeds either way, but a bare `flyte.Image` name has no registry inside a pod and the child then cannot pull it. Reuse this container's image (`$FLYTE_INTERNAL_IMAGE`) or a public one. When you genuinely need new packages, use `flyte.sandbox.create(name=..., code=..., packages=[...])`, which goes through the platform's builder and *can* build from inside a run. There is no `pip` at runtime in a sandbox job -- declare packages up front; a wheel URL is a valid entry.
2. **Ask for spot first for CPU work -- but spot has no GPUs.** `interruptible=True` is cheaper and draws from a different pool than the on-demand nodes this cluster has exhausted, so for CPU work it is both less expensive and more likely to be placed. It is also *mutually exclusive with a GPU here*: the only spot nodepools are `awst3axlargespot` and `awsc54xlargespot`, and both report `gpu=0`, so `interruptible=True` together with `gpu=1` is infeasible every time, whichever device you name. **A GPU means `interruptible=False`.** For CPU child work, pair spot with a queue bound and fall back rather than wait:

```python
from datetime import timedelta
import flyte.errors

bound = flyte.Timeout(max_queued_time=timedelta(minutes=5))
try:
    # Cheaper, and a separate pool. CPU only -- see above.
    await train.override(interruptible=True, timeout=bound).aio(0.01)
except flyte.errors.MaxQueuedTimeExceededError:
    # Clear the timeout: the queue bound carries through override().
    await train.override(interruptible=False, timeout=flyte.Timeout()).aio(0.01)
```

`max_runtime` does not help here -- it only starts counting once a pod is placed, so without `max_queued_time` an unplaceable job waits forever in `WAITING_FOR_RESOURCES`, which is not a failure and not progress. Note `max_queued_time` is per *attempt*, so retries multiply the wait. A preempted spot task is retried on the platform's budget, not out of your `retries`, so spot costs you the work in flight rather than an attempt. Only reach for on-demand when losing that work would actually hurt, or when spot could not be placed.

**Finding out what hardware you can have.** No API reports free capacity -- but you do not have to guess, because the scheduler explains itself. An *impossible* request is rejected by admission in about a second, with a verdict naming every nodepool it tried and what did not fit:

```
infeasible: no cluster of queue "oc-production" has a nodepool that can run every pod
of the action among its spot nodepools (the attempt is interruptible; mark the task
as non-interruptible, or add a spot nodepool); pod "primary" (cpu=2000m memory=8Gi
gpu=1 (nvidia-t4)) fits no nodepool: awst3axlargespot: requests gpu=1 but a node has
gpu=0; awsc54xlargespot: requests gpu=1 but a node has gpu=0
```

That is authoritative and it usually contains the fix verbatim. So **probe with a trivial job at the shape you want before building a pipeline around it**, and read the error rather than reasoning about it. Two things it will not tell you up front:

- **On-demand GPUs are available, and `nvidia-tesla-t4` is confirmed placeable** (`interruptible=False`, `gpu=1`). L40S nodes exist too but are tainted. Do not assume a device class is unavailable without probing for it -- and prefer not to name one at all unless you need a specific one, so the scheduler can use whatever is free.
- **Every task gets at least ~1 CPU and ~1Gi** whatever you ask for, so asking for less buys nothing.

A request that is *possible but currently unsatisfiable* behaves differently from an impossible one: it sits in `WAITING_FOR_RESOURCES`, which is neither failure nor progress, and which is what `max_queued_time` is for.

**Data too big for git lives in the artifact service, not the repo.** Datasets, audio, model weights, anything large: look there *first* before asking anyone to stage something, and publish your own outputs there rather than committing them.

```python
import flyte.remote as remote
from flyte.io import Dir

# Find what already exists -- it may be exactly what you were about to ask for.
for a in remote.Artifact.listall():
    print(a.name, a.version)

art = remote.Artifact.get('voice-target-audio')   # or version='...'
d = await art.to_python(Dir)   # pass the type: guessing fails for a directory
await d.download('./data')

# Publishing. upload_dir goes through the control plane, so it needs no
# cloud credentials of its own.
uri = remote.upload_dir(Path('./my_outputs'))
remote.Artifact.create(
    Dir.from_existing_remote(uri),
    name='my-dataset', version='v1',
    description='<=255 chars',
    attrs={'rows': '1000'},    # searchable; put the caveats here
)
```

Three traps, all of which cost time: `upload_dir` and `upload_file` are syncified and return a value, so `await` on them raises `TypeError`, while `to_python` *is* a coroutine and must be awaited -- the API is not consistent, so check. `to_python()` needs the type passed explicitly for a `Dir` or `File` (`No transformers could reverse Flyte literal type blob` means you omitted it). And `description` is capped at 255 characters. Read `attrs` before trusting an artifact's contents: whoever published it may have recorded that part of it is suspect.

**Delegating a whole chunk of work** goes to a sub-agent, which is also a child action with its own logs:

```python
from flyte_agent_factory.agent import subagent
summary, artifacts = await subagent(brief='...', role='verify', workdir=None)
```

Nothing it produces is merged automatically -- you review and take what you want. A sub-agent's action is not yours to abort; ask it to finish instead.
## Recording a demo of this work

  ```sh
  ffmpeg -i in.webm -c:v libx264 -preset slow -crf 20 -pix_fmt yuv420p \

  ```
  `-pix_fmt yuv420p` and `-movflags +faststart` are not optional decoration: without the first some players show nothing, and without the second the file will not start playing until it has fully downloaded.

Rebase before pushing; `main` moves while you work.

**Nothing on screen should reveal that an agent built this** unless the demo is explicitly about the agent: no `claude-*` task names, no `BRIEF.md` or `CLAUDE.md`, no session UI, no terminal with the agent in it. Check every frame you keep. If you cannot produce a clean view, say so with `flyte-note` and leave the section out rather than filming the scaffolding.

### Who it is for, and what it is actually about

Decide these two things before you plan a single beat. Both go in the manifest, as `audience` and `subject`, and the README repeats them in its first two lines.

**Who is watching, and what are they deciding?** Name the role, what that person is accountable for, and the decision they are making while the video plays -- usually *is this worth an hour of my team's time?*. A platform lead, a data science manager and a CTO are watching for different things, and a demo that tries to satisfy all three satisfies none. Pick one. Everything in the video serves that person's job, and anything that only interests you comes out.

**What is the subject, and what is merely the example?** The subject is the capability you want remembered. The example is one concrete thing built with it, chosen because it is legible in thirty seconds. Confusing the two produces a demo that sells the example and buries the product.

The gateway demo is the case to learn from. The subject is *a fast, pluggable, scalable LLM gateway*: every call in your org through one endpoint, one key, with policy you own in front of the model. The example is *PII detection choosing between an external model and a self-hosted one*. PII routing is not a feature of the gateway -- it is one of countless things you could plug in, and the viewer should come away thinking "I could put my own policy there", not "this product does PII". Say the subject out loud at the start and again at the end; let the example carry the middle.

So, when you choose what to show:

- **Open on their problem, not on the product.** The first line is a situation the viewer recognises. Nobody has ever kept watching because a video opened by naming a component.
- **Show the what before the how.** The result first, the mechanism second, and only as much mechanism as makes the result believable.
- **One workflow, one use case.** Capabilities you are not showing are not the subject. A feature tour is not a demo.
- **Stay inside the boundary of what the thing actually does.** A claim the viewer can disprove in five minutes costs you the rest of the video. Where the example is one option among many, say so; where a number has a caveat, give the caveat in the same breath.
- **Finish on the result and what it means**, not on a recap of the sections.

### The three channels say different things

A slide, the screen and the narration are three channels, and a demo is good when they carry *different* information:

- **Bullets state the high-level point.** A few words, the claim or the number. They are read in a second and then ignored.
- **Visuals show what is happening.** The run, the routing decision, the curve, the thing working. This is the evidence.
- **Narration expands and contextualises.** Why this matters, what it would have cost otherwise, what the viewer should conclude, the caveat. It is the only channel that can say *so what*.

**Narration that reads the slide aloud is wasted.** If a line of voiceover is the words on screen with filler around them, the viewer has already read it and you have spent three seconds saying nothing. Write the slide first, then write narration that would still be worth hearing with the slide hidden. Check each line that way before you synthesise it.

Writing the lines: short spoken sentences, one idea each. Verbs rather than labels -- "ten labelled images per class gets you there", not "the label-efficiency capability". Read it back to yourself; anything you would not say to a colleague, rewrite. Keep it short enough that each line finishes while its slide is still on screen.

Use realistic, believable data. Obviously synthetic names and `foo`/`bar` placeholders make a demo feel like a toy; plausible-but-fake is what you want.

### Making it watchable

**Short and punchy is the default.** Unless the brief says otherwise, aim for **30-60 seconds**: one idea per section, three or four sections, nothing that does not earn its place. A viewer decides in the first five seconds whether to keep watching, so lead with the interesting claim rather than setting it up. Cut anything you would skip.

- **Plan the sequence, then record once.** Decide the beats, get the thing into a clean state, rehearse by walking it without recording if you need to.
- **A visible mistake or a recovery means re-record.** Nobody sends a prospect a take where something went wrong and got fixed on camera.
- **Show the result, not the machinery.** A terminal scrolling installs is not a demo. Show what was built and that it works.
- **Pause on anything you want seen.** `browser_wait_for` with a second or two, so a viewer can actually read a number before it disappears.

### On brand

If `.claude-flyte/standards/brand.md` exists, it is the configured brand source: follow it; do not redecide. Otherwise, if `BRAND.md` exists in the repo, follow it and do not redecide any of it. If it does not, derive it: look at `union.ai` and the Union console in the browser, take the palette, the type treatment and the tone, and **write what you derived into `BRAND.md` and commit it**; say explicitly that it was inferred, so the next demo inherits it rather than guessing again. Say in your report that you inferred it and it wants checking.

Legible beats decorative: dark background, high contrast, one accent colour, generous type, no stock imagery, no gradients for their own sake. A number a viewer cannot read is a wasted slide.

### Sound, and why the pieces are kept

**A browser recording has no audio track.** Narration and music cannot be captured, only composited afterwards with `ffmpeg`, which is in this image. That is also what makes a demo editable: a later instruction to change the music or reword one slide should re-render from the kept pieces, never re-record the demo.

So compose rather than capture:

1. Build each section as its own file under `assets/slides/`.
2. Record the screen capture and keep it as `assets/screen.webm`.
3. Put narration and music under `assets/audio/`, one file per line of narration so a single line can be redone.
   **Do not synthesise a music bed.** A generated tone is a hum, and a hum is worse than silence -- it makes a demo feel cheap in a way no viewer can articulate but everyone notices. Use a music file only if one is actually committed in the repo; otherwise narration alone, or no audio at all.
4. Composite with `ffmpeg` into the final video at the top of the package, and record the exact command in the manifest so the next person can re-run it.
   **Normalise the loudness, and check it.** Synthesised narration comes out quiet: a demo shipped at -25.5 LUFS, about 10 dB under normal dialogue, and the first thing the viewer asked was whether it was supposed to have audio at all. End the chain with `-af loudnorm=I=-16:TP=-1.5:LRA=11`, then *verify* with `ffmpeg -i out.mp4 -af volumedetect -f null -` and expect a mean around -18 dB. Note that `volumedetect` prints at info level, so it says nothing under `-v error`.
5. Write `assets/manifest.json` describing the composition: the `audience` and `subject` lines from above, then a `sections` list, in order, each with a `title` and whichever of `slide`, `voiceover`, `music`, `start` and `duration` apply. Paths are relative to the package root. **The run fails if the manifest is missing or points at a file that is not there** -- a dangling reference is worse than none, because somebody will follow it.

**No voice model is available**, so build the demo with music only and leave the `voiceover` keys out of the manifest rather than pointing them at files that do not exist. Do not substitute a different TTS voice: a demo narrated in somebody else's voice is worse than a silent one.

**No console credential is available in this pod**, so a console URL will redirect to a sign-in page. Leave that section out rather than filming a login screen.

Two things about that page, both learned the hard way:

- It reports **~84 console errors even when it renders correctly**, so console errors are not a failure signal here.
- It is a heavy single-page app: give it a few seconds before snapshotting or recording.

**Navigating to a console URL without authorisation redirects you to `signin.example.org`. That is expected, not a sign the console is unreachable.** A previous demo read that redirect as a network failure, reported that the pod could not reach the console, and shipped a take with a placeholder chapter. The pod reaches it fine.

### If you have no browser tools

Check at the start that `browser_start_video` and `browser_navigate` are actually available to you. If they are not, **do not build the package anyway** -- say so with `flyte-note` and stop. A package without a video is not a partial success, it is the one outcome that looks like success and is not: the run will fail on it, and silently working around a missing capability wastes everyone's time.

### Before you finish

Check your own package the way the run will: the folder exists, there is a `.webm` in it that is more than a few KB, there is a `README.md`, and there is code. Then watch your own take -- `browser_navigate` to the file and play it -- and ask whether you would send it to a customer. If not, re-record.

Report what you did with `flyte-note`, and use `ask-human` if the brief leaves the point of the demo genuinely unclear.
